## Verdict global

Projet sérieux, bien au-delà d'un prototype. Architecture claire (Room = file de
tours + routing, Registry = roster/seats, Participant = hat handle, SeatRuntime
= propriétaire de session). La philosophie « norms, not loops » est appliquée de
façon cohérente, et la culture de dégradation gracieuse est exemplaire —
supervisor mort → auto, reviewer de gate absent → gate désarmé, évaluateur
absent → completion sans vérif, save en échec → log + notice jamais de crash.
Les commentaires documentent chaque décision non triviale avec la date,
l'incident observé et le raisonnement — une mine pour la maintenance.

## Points forts

1. **Tests** : 1986 tests / 114 fichiers, couvrant des cas tordus (path
   traversal, ask-user-resume, turn-salvage, supervised-chain-repro).
   `parsePresetFile` avec warnings non-bloquants est un bon pattern.
2. **Invariants anti-boucle en profondeur** : chain-hop budget, refused-routes
   cap par tour, budget d'itérations de goal, no-handoff menu one-shot par agent
   par itération. Chaque couche a son échappatoire bornée.
3. **Sérialisation des écritures** (`store.writeChain` + tmp unique + flush au
   shutdown + seal) — raisonnement sur les races correct et documenté.
4. **`handoff-gates.ts`** : logique pure, testable, limites explicites
   documentées (bash side-effects non vus, tour courant seulement).
   `globToRegExp` correct.
5. **Observabilité** : chaque dégradation laisse une trace dans le transcript
   (⚠, ≡, ✓/✗). « Never silent » appliqué partout.
6. Sécurité de base : bind `127.0.0.1` hardcodé, CORS restreint, rate limiting
   sur `/messages` et `/shell`, validation systématique des bodies, outils
   confinés au workspace.

## Problèmes trouvés

### 1. Path traversal dans `/api/media/:filename` (sécurité, réel)

`src/server.ts` :

```ts
const filePath = join(mediaDir(), filename)
await access(filePath)
res.sendFile(filePath)
```

Express décode le percent-encoding des params :
`GET /api/media/..%2F..%2Fsessions%2F...` résout hors de `mediaDir/`. Le check
`extname` limite aux extensions image, mais n'importe quel
`.png/.jpg/.jpeg/.webp/.gif` lisible par le process sur le disque est servi.
Impact limité par le bind localhost, mais c'est la seule route qui sert des
fichiers arbitraires. Correctif en une ligne avec l'utilitaire existant :

```ts
import { assertInside } from "./path-guard.js"
const filePath = join(mediaDir(), filename)
try {
  assertInside(mediaDir(), filePath)
  await access(filePath)
  res.sendFile(filePath)
} catch { res.status(404).json({ error: "image not found" }) }
```

### 2. `path-guard` ne résout pas les symlinks (à documenter)

`assertInside` est lexical (`resolve` + `relative`). Un symlink dans le
workspace pointant vers l'extérieur passe — et un agent avec `bash` peut créer
ce symlink. Limitation acceptable vu que `bash` est déjà documenté
« trusted-local only », mais le commentaire de `path-guard.ts` devrait le dire
explicitement puisque `read`/`write`/`edit` prétendent être confinés. Durcissement
possible : `realpath` sur la cible avant le check.

### 3. Abort pendant l'attente du `LocalModelLock` (trou potentiel)

Dans `executeAgent` : `running.add(target)` puis
`await this.localLock.acquire(...)`. Si l'utilisateur aborte pendant que l'agent
attend le lock, `abortCurrent()` appelle `p.abort()` sur une session qui ne
stream pas encore (no-op), et quand le slot se libère, **le tour démarre quand
même**. Fenêtre réelle avec `PIPELINE_LOCAL_SLOTS=1` et plusieurs rooms.
Suggestion : après l'acquisition, court-circuiter si `this.aborted` avant
`target.run()` :

```ts
if (isLocal && this.localLock) { await this.localLock.acquire(this.roomId); lockAcquired = true }
if (this.aborted) return null   // acquis trop tard — le Stop gagne
```

### 4. `store.list()` reparse tout à chaque save (scalabilité)

`broadcastConversations()` est appelée après **chaque** `saveCurrent()`
(debouncée à 400 ms), et `list()` fait `readdir` + `JSON.parse` de **chaque**
fichier de conversation — transcripts complets inclus. Sur une instance de
longue durée avec des dizaines de conversations de plusieurs centaines de Ko,
chaque save relit l'intégralité du répertoire pour 5 champs de meta. Correct à
court terme, premier goulot à venir. Options : cache de métas invalidé au write,
ou fichier `<id>.meta.json` séparé.

### 5. Duplication legacy `/api/*` vs room-scoped router (~300 lignes)

Les handlers `PATCH /api/participants/:id` et `PATCH /api/settings` existent en
deux copies quasi verbatim (default room vs `roomRouter`). Classe de bug déjà
produite (le compact qui broadcast sur un chemin et pas l'autre — le
`353K`-stuck). Le bon pattern existe déjà — `doSavePreset`/`doLoadPreset`/
`doApplyPreset` prennent le `Room` en paramètre. Extraire `doPatchParticipant(r,
id, body, res)` et `doPatchSettings(r, body, res)` et faire déléguer les deux
routes élimine la classe entière.

### 6. God files

`room.ts` (2981 lignes) porte : transcript, queue, 4 modes de routing, goal-eval
loop, drift de presets, lifecycle des conversations, shell, steering, slash
commands, plan-routing. `server.ts` (2320) mélange provisioning, presets IO,
OAuth, rooms CRUD. Ça tient grâce aux commentaires, mais chaque feature augmente
le risque de divergence N-seam. Découpage naturel possible : `room-goals.ts`
(submitGoal/runGoalEval/evalOutcome), `room-slash.ts` (handleSlashCommand),
`room-conversations.ts` (lifecycle + persistence).

### 7. Mineurs

- **SSE sans heartbeat** : `sse.ts` n'envoie aucun `:ping` périodique. Une
  connexion idle à travers un proxy peut mourir silencieusement. Un
  `setInterval(() => broadcast comment, 30s)` suffit.
- **OAuth sans timeout** : `pendingOAuthInputs` peut garder une promise
  indéfiniment si l'utilisateur abandonne le flow (ni cancel, ni input). Un
  timeout de 5 min qui reject nettoierait.
- **`config.port`** : `Number(process.env.PORT ?? 5300)` sans garde NaN —
  `PORT=abc` → erreur cryptique au listen. `PIPELINE_MAX_ROOMS` et
  `PIPELINE_LOCAL_SLOTS` ont le garde-fou `|| 8` mais pas `PORT`.
- **F7 (knownissues, ouvert)** — steer pendant un retry provider crashe le tour.
  Vu la qualité du salvage implémenté partout ailleurs (`stopReason`, markers),
  ça semble à portée d'une session de repro.
- **`npm run dev` vs `npm start`** : `predev` peut-il échouer silencieusement ?
  Non vérifié.

## Problèmes trouvés (partie 2)

### 8. `acquireTurn` n'est pas annulable — un hat peut attendre le lock indéfiniment

`seat-runtime.ts` :

```ts
async acquireTurn(hatId: string, thinkingLevel?: ThinkingLevel): Promise<() => void> {
  const prev = this.turnLock
  let release!: () => void
  this.turnLock = new Promise<void>((res) => (release = res))
  await prev
  // …
}
```

Un hat dont le tour est enqueued derrière un autre hat du même seat **ne peut
pas être aborté** : il attend `prev`, qui ne se résout qu'à la fin du tour en
cours. Si l'utilisateur aborte la room pendant cette attente, `abortCurrent()`
appelle `p.abort()` sur la session — mais le hat en attente n'a pas encore
démarré, donc son `externallyAborted` est mis sur une session qui stream (celle
de l'autre hat), et quand `prev` se résout, **le hat en attente démarre quand
même son tour**. Même classe de bug que le point 3 (LocalModelLock), une couche
plus bas. Avec `PIPELINE_LOCAL_SLOTS=1` les fenêtres se composent (attente lock
global → attente lock seat). Correctif analogue : après `await prev`, vérifier
un flag d'annulation posé par `Participant.abort()` et retourner sans exécuter.

### 9. SSRF dans `web_read` (documenté ici, pas dans le code)

`custom-tools/web-read.ts` : Jina Reader fetch n'importe quelle URL fournie par
le modèle — y compris `http://localhost:5300/api/...` (le serveur lui-même),
`http://192.168.x.x`, `http://169.254.169.254/` (metadata cloud), ou une URL
`file://` si Jina l'honorait. Jina fait le fetch côté tiers donc le pire cas
direct est limité, mais le contenu extrait de cibles internes revient dans le
contexte de l'agent. Sur une stack local-first où l'agent peut être un 9B peu
fiable, c'est un vecteur d'exfiltration de contenu interne vers le contexte
d'un modèle cloud. `web_search`/`youcom_search` passent par des services de
recherche (moins sensible). Recommandation : un commentaire en tête de
`web-read.ts` assumant le choix (ou un blocage des hôtes RFC1918/loopback
côté prompt), et mention dans le README. Sévérité : faible — tous les tools web
sont opt-in par persona.

### 10. Race manifest/meta `writeFile` sur `.tmp` partagé (théorique, bornée)

`room-manager.ts` sérialise via `saveQueue`/`metaQueue`, mais le tmp path est
fixe (`rooms.json.tmp`, `meta.json.tmp`) contrairement à `store.ts` qui a un
suffixe unique par write. Les queues protègent en pratique — sauf si deux
`RoomManager` partagent un `sessionsDir` (tests parallèles avec le même dir, ou
un second process sur la même instance — scénario que le code supporte
implicitement en lisant le manifest au boot). `store.ts` a appris la leçon
(commentaire `writeSeq`) ; `room-manager.ts` ne l'a pas reçue. Fix trivial :
même pattern pid+seq. Sévérité : faible (chemins de test uniquement en
pratique).

### 11. `restoreRooms` : une room dégradée (mount échoué) persiste `sshTarget` mais pointe sur le workspace partagé

Quand le re-mount sshfs échoue au boot, la room est restaurée avec
`workspaceDir = config.workspaceDir` (le workspace principal du pipeline) et
`remote = !!(mount || sshTarget)` = true — donc pas de snapshots. Mais ses
agents ont les outils fichiers confinés sur **le workspace principal**, pas sur
leur scope prévu : un agent de la room distante peut lire/écrire les fichiers
du workspace local pendant que la room croit être « dégradée ». Le log le dit
(`Restoring in degraded mode`), mais l'effet est plus large que « la room est
en panne » : elle devient active sur un scope qu'elle ne devrait pas voir.
Alternative : restaurer la room avec un roster entièrement inactif, ou refuser
le restore et laisser la room dans `listResumableRooms` pour resume manuel.
Choix de design à activer explicitement — l'actuel privilégie la continuité,
ce qui est défendable, mais le commentaire minimise l'effet réel.

### 12. `model.ts` — `splitRef` sur un ref sans provider donne `provider: ""`

`resolveModelRef` : un persona model `"claude-opus-5"` (sans `/`) devient
`{provider: "", id: "claude-opus-5"}` → `provider !== "local"` → si cloud
désactivé, warning et fallback (OK) ; si cloud activé, `find("", id)` →
probablement undefined → fallback. Comportement final correct (fallback), mais
le warning dit « non-local » alors que le vrai problème est « malformé ».
Cosmétique.

### 13. Points positifs supplémentaires à noter

- **`handoff.ts`** : le commentaire `executionMode: "sequential"` documente un
  TOCTOU réel observé (deux handoffs batched passant tous les deux le guard) —
  et le fix est au bon niveau (déclaratif dans le schema, pas un mutex).
- **`turn-parts.ts`** : l'invariant « le segment ouvert est toujours le dernier
  élément » rend le tri inutile par construction ; le `seq` wire-side qui
  garantit live == persisted est une excellente idée.
- **`reasoning-budget.ts`** : framing positif documenté (ironic-process
  rebound) — quelqu'un a lu la littérature. Le `breached` one-shot par grant
  est correct.
- **`batch-terminate-guard.ts`** : wrap d'une propriété publique mutable avec
  chaînage du handler précédent — hack assumé, borné, commenté avec la preuve
  (agent-loop.js vendored).
- **`preset-hydration.ts`** : la paire strip/rehydrate rend l'héritage de seed
  permanent ; le doc comment sur le data loss de `systemPrompt` (strip
  inconditionnel) est honnête et pointe le ROADMAP #6 au lieu de décider en
  silence.
- **`sshfs.ts`** : BatchMode=yes évite le hang sur prompt de mot de passe ;
  mount idempotent avec cleanup préalable ; teardown toujours best-effort.
- **`plan-routing.ts`** : parsing défensif total (jamais de throw), le
  passage « explicit adoption » avec l'incident planner↔tester est un modèle
  de post-mortem appliqué au code.

### 14. Packages et frontends (skim)

- **`preset-schema`** : schéma TypeBox avec `additionalProperties: false` et
  runtime validation — bien. Le commentaire sur `cursor` qui « leaks into
  saved files » suggère un champ runtime qui ne devrait pas être sérialisé —
  vérifier si `stripSeedFields` ou le writer le filtre (le writer de preset
  côté server passe par `stripSeedFields` qui ne retire que `systemPrompt` et
  `skills` ; `cursor` survit dans un preset sauvegardé depuis une room live →
  sera rechargé dans `rehydrateSeedFields` → propagé dans `registry.reset`
  comme savedCursor. Effet : une room chargée depuis un preset hérite du
  cursor de la room qui l'a sauvegardé. Probablement inoffensif (le cursor
  est clampé par la longueur du transcript… mais le transcript d'une nouvelle
  discussion est vide → cursor > 0 dans un transcript vide = l'agent saute
  les premiers messages ?). **À vérifier** : `loadPreset`/`startFresh` mint un
  nouveau convId → session root vide → sessions fraîches → cursor restauré
  depuis PersonaState.savedCursor… `registry.create` : `participant.cursor =
  participant.resumed ? … : 0` — non resumed → 0. OK, faux problème : le
  cursor du preset n'atterrit que sur des sessions resumed. Mais il est
  stocké dans le fichier preset sans raison — le filtrer au save serait plus
  propre.
- **`client-core`** : architecture store/reducer pure + effets, host-neutral
  (browser EventSource injectable) — le partage TUI/web est bien fait.
- **Web UI** : aucun `dangerouslySetInnerHTML` — le rendu markdown doit être
  fait côté composants ; pas de risque XSS direct repéré au skim.
- **TUI** : 4211 lignes de commandes/composants, migration pi-tui en cours
  (d'après bugs.txt). Non relu en détail.
